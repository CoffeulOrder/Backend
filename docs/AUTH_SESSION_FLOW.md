# 비밀번호 재설정·변경과 로그인 갱신 계약

## 비밀번호 찾기

기존 비밀번호를 반환하거나 임시 비밀번호를 발급하지 않는다. 사용자가 이메일 인증 후 새 비밀번호를 직접 정한다.

1. `POST /api/v1/verifications/email`: `email`, `purpose: PASSWORD_RESET`.
2. `POST /api/v1/verifications/email/confirm`: 동일한 `email`·`purpose`와 인증번호 `code`.
3. 받은 `verificationToken`과 사용자가 입력한 `newPassword`를 `POST /api/v1/members/password-reset`에 전달한다.
4. 성공하면 새 비밀번호로 로그인한다. 인증 토큰은 용도·만료·소비 상태를 검사한다.

로그인된 사용자의 비밀번호 변경은 `PATCH /api/v1/members/me/password`다. Bearer 인증과 `currentPassword`·`newPassword`를 보낸다.
두 경로의 비밀번호 규칙은 영문·숫자 포함, 최소 8자, UTF-8 기준 최대 72바이트다.

## 로그인 정보 폐기 보완

로그아웃 직후와 비밀번호 변경/재설정 후, 직전에 회전한 refresh 토큰이 정상 재시도의 30초 유예로 새 토큰을 받는 문제를 네 회귀 시나리오에서 재현했다.

- 정상 refresh 회전의 30초 재시도 유예는 유지한다.
- 로그아웃은 해당 로그인 계열의 유효한 refresh 토큰을 모두 즉시 만료시킨다. 회전된 선행 토큰·동시 재시도에서 파생된 토큰도 포함하며 다른 기기의 별도 로그인 계열은 유지한다.
- 비밀번호 변경·재설정·탈퇴는 해당 회원의 유효한 모든 계열을 만료시킨다. revokedAt이 찍혔지만 유예가 남은 선행 토큰도 포함한다.
- 로그인·회전·명시적 폐기는 계정 행을 먼저 잠근 뒤 토큰을 읽거나 발급한다. 회전이 먼저 시작됐으면 명시적 폐기가 그 결과까지 만료시키고, 폐기가 먼저 끝났으면 refresh를 401/AUTH_003으로 거절한다.
- DB 스키마·외부 API의 요청/응답 형식·기존 HTTP 성공 코드는 바꾸지 않는다.

## FE 처리

- 로그인/refresh 응답의 accessToken·refreshToken은 함께 교체해 저장한다.
- 로그아웃 성공 또는 refresh의 401/AUTH_003이면 로컬 로그인 정보를 지우고 로그인 화면으로 이동한다.
- 비밀번호 변경·재설정 성공 뒤에는 새 비밀번호로 다시 로그인한다.
- 이번 보완은 refresh 재발급 경로를 폐기한다. 기존 access JWT 자체를 블랙리스트로 즉시 취소하는 기능은 없으므로, FE는 로그아웃 뒤 보관 중인 accessToken도 삭제해야 한다.
- 토큰·비밀번호를 사용자 안내 문구, 분석 이벤트, 디버그 로그에 포함하지 않는다.
